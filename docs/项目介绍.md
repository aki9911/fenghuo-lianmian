# 烽火连绵个人项目经历

建议放在“项目经历”第一项，与现有《燕云十六声》战令拆解形成“系统分析—玩法设计—原型落地”的能力展示。项目时间可写 2026.11—至今。

**《烽火连绵》边镇守御 PvE 原型｜系统策划 / AI 辅助原型开发｜个人项目**

- **项目目标：** 基于对《燕云十六声》PvE 体验的拆解，围绕版本内容消耗后持续参与目标不足的体验假设，探索以边镇守御和集体战役反馈延长内容生命周期的玩法方案。
- **玩法设计：** 参考《地狱潜兵》的长期战役调度与《战地1》的阶段防守，设计“实时镇务—资源筹备—暂停布阵—实时防守—撤离评价—战后恢复”循环，将物资投入、军民伤亡与守城结果关联；规划全服抵抗成果影响后续攻势和故事走向。
- **AI 工作流：** 使用 Codex 与多 Agent 按运营数值、战斗关卡和表现模块拆分任务，建立分册策划、公共接口和验收约束；结合 Excel→JSON 配置及 Godot MCP，探索从需求表达、代码生成到引擎调试和回归验证的协作流程。
- **原型成果：** 落地 Godot 第三人称可玩灰盒，接通建筑交互、实时生产、四阶段防守、即时布阵、小队军令和本地战报；完成 100 敌军 / 50 友军在场规模验证，并通过人口守恒、士气边界、碰撞与实际撤离测试。全服联动与动态故事仍为后续设计范围。

## 精简版

基于对《燕云十六声》PvE 体验的拆解，围绕版本内容消耗后的持续参与需求，设计“实时镇务—资源筹备—阶段守城—撤离评价—战后恢复”循环，并规划全服抵抗结果影响后续战役与故事。使用 Codex、多 Agent 与 Godot MCP，建立分册策划、接口约束、Excel 配置导入和回归验证流程，将方案落地为第三人称可玩灰盒；已实现建筑交互、即时布阵、小队指挥及本地战报，验证 100 敌军 / 50 友军在场规模。长期全服联动尚未接入。

## 面试时的表述边界

“官方与玩家之间的 PvP”建议改为“官方战役调度与玩家集体抵抗的长期 PvE”。官方控制攻势和事件节奏，玩家通过战果和支援参与叙事演变，并不是玩家直接互相对抗。

“版本后期缺少耐玩内容”在当前材料中属于个人观察和待验证假设，不能写成已证实的全体玩家结论。本项目目前验证了实现可行性，尚未开展玩家留存实验，不能声称提升留存率或降低开发成本的具体比例。

可讲述的一次实际迭代：为角色加入实体碰撞后，发现守军阵位堵住居民撤离路线；通过调整集结区、阵位和安全走廊，在保留碰撞的场景中验证 150 人完整撤出。该案例能体现提出约束、检查 AI 产物和用测试复核设计的过程。
